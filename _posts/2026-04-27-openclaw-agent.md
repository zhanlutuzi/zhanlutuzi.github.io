我最开始看 OpenClaw 的时候，以为它只是又一个 AI Agent 项目。

这几年类似的项目太多了。AutoGPT 火过，LangChain 火过，Claude Code、Cursor、Manus、各种浏览器 Agent 和自动化工具也都在讲同一个故事：AI 不应该只会聊天，它应该能替人做事。

但 OpenClaw 让我停下来多看了几眼。

不是因为它的功能列表有多新，而是因为它在很短的时间里，把 AI Agent 这件事里的几组矛盾全都暴露出来了：

```text
本地优先
  vs 云端易用

真实执行能力
  vs 真实安全风险

开源社区信任
  vs 大公司资源介入

个人助理想象
  vs 操作系统级权限
```

这篇文章不是一份完整的产品评测。我更想把 OpenClaw 当成一个切片：当 AI 从“回答问题”走向“替我行动”，一个开源项目会怎样突然长大，又会怎样被自己的能力反噬。

## 它真正吸引人的地方，不是聊天，而是执行

OpenClaw 的定位很直接：一个运行在你自己设备上的个人 AI 助理。

它不是让你打开一个网页，在聊天框里问问题。更准确地说，它想把 AI 放到你已经在用的消息渠道里：WhatsApp、Telegram、Slack、Discord、Signal、iMessage，甚至微信、QQ 等。你在这些入口里给它发消息，它再通过 Gateway 去调度会话、工具、文件、浏览器、定时任务和其他自动化能力。

OpenClaw 官方 README 里有一句话很关键：

> The Gateway is just the control plane — the product is the assistant.

这句话可以翻译成更直白的版本：

> 聊天入口不是产品本身，真正的产品是那个能持续运行、能连接工具、能执行动作的助理。

这和传统聊天机器人的差别很大。

传统聊天机器人更像一个随叫随到的顾问。你问，它答。它可以很聪明，但多数时候不会真正碰你的系统。

OpenClaw 这类工具想做的是另一件事：

```text
消息入口
  -> Gateway 控制平面
  -> 模型推理
  -> 工具调用
  -> 文件 / 浏览器 / 应用 / 消息渠道
  -> 执行结果回到用户
```

一旦把“执行”放进系统，AI Agent 就不再只是语言产品，而开始变成一种个人自动化基础设施。

这也是它爆红的原因之一。很多人已经对“更会聊天的 AI”有点麻木了，但“我能在 Telegram 里发一句话，让自己机器上的 Agent 去整理文件、发消息、跑脚本、查网页、记住上下文”，听起来仍然很像未来。

## OpenClaw 的故事，其实是本地优先叙事的回潮

OpenClaw 最有意思的地方，是它选择了“本地优先”这条路线。

过去几年，AI 产品的默认形态是云端 SaaS：账号登录，数据上传，模型推理在服务商那里完成，交互历史、文件、权限也都尽量被平台托管。这样做的好处很明显：上手快、维护少、体验统一，适合普通用户。

但云端 SaaS 也有一个越来越明显的问题：用户必须交出控制权。

你把文件交给它，把会话交给它，把浏览器任务交给它，把邮箱、日历、网盘、代码仓库的权限也交给它。只要 Agent 真的开始帮你做事，它接触到的就不再是几段无关紧要的聊天记录，而是你的工作流本身。

OpenClaw 的吸引力恰好来自这里。它给技术用户的承诺不是“最省事”，而是：

```text
运行在我的机器上
数据主要留在我的环境里
工具权限由我配置
模型供应商可以替换
自动化逻辑可以自己改
```

这更像 Linux，而不像 iPhone。

iPhone 路线的终点是：普通用户不需要理解底层，只要相信平台。

Linux 路线的终点是：用户愿意承担复杂度，因为他要控制权、可审计性和可替换性。

OpenClaw 现在明显站在第二条路线上。它的上手门槛不低，安全配置也不能省略，但它给了一部分人很强的心理确定性：这个 Agent 不是一个黑盒服务，而是我可以拆开看的系统。

## 爆红之后，名字先失控了

OpenClaw 早期并不叫 OpenClaw。

公开资料里能看到的脉络大致是：它最初叫 Clawdbot，后来因为名称和 Anthropic 的 Claude 容易混淆，改成 Moltbot，最后变成 OpenClaw。

这段改名故事看起来像八卦，但它其实说明了一个开源项目突然爆红后的典型问题：

> 项目增长速度超过了治理能力。

个人项目、小团队项目或者周末实验，在早期不需要完整的品牌、法务、安全、社区治理、发布流程。只要代码有用，自然有人来。

但一旦它成为全球开发者围观的项目，很多原本“不重要”的东西会突然变得重要：

```text
项目名称会变成商标问题
安装脚本会变成供应链问题
默认配置会变成安全问题
贡献者规模会变成治理问题
创始人个人选择会变成生态信任问题
```

OpenClaw 的改名风波就是第一个信号：它已经不再是一个只有作者和少数用户关心的玩具了。

## 更大的问题是：它真的能碰你的电脑

OpenClaw 让我真正警惕的地方，不是改名，而是安全。

如果一个 AI 只能聊天，它说错话的代价通常是误导你。

如果一个 AI 能读文件、写文件、发消息、跑脚本、连浏览器、连邮箱、连团队协作工具，它出问题的代价就变了。

这时候风险不再只是“幻觉”，而是：

```text
读到不该读的文件
把消息发给不该发的人
执行了用户没意识到后果的命令
被陌生消息诱导执行操作
暴露在公网后被别人接管
把 API Key、Token、聊天历史泄露出去
```

OpenClaw 官方文档现在已经把安全默认值写得很重。例如 README 提醒用户把来自 DM 的输入当成不可信输入；未知发送者默认需要 pairing；公开接收陌生 DM 需要显式打开；`openclaw doctor` 可以检查高风险配置。它也明确说明：默认情况下，主会话里的工具会在宿主机上运行，也就是说 Agent 在“只有你自己使用”的场景下可以拥有很高权限。

这句话非常重要。

很多人讨论 AI Agent 安全时，仍然停留在模型安全、提示词注入、越狱这些词上。但 OpenClaw 这类项目的核心风险更朴素：

> 你给了它多大权限，它被误用或被攻破时，别人就可能拿到多大权限。

TechRadar 在 2026 年 4 月报道了 SecurityScorecard 对 OpenClaw 暴露实例的研究：他们识别出 40,214 个暴露在互联网上的 OpenClaw 实例，其中 28,663 个唯一 IP 的控制面板可被公网访问，约 63% 的观测部署看起来存在远程代码执行风险。

这个数字是否会随时间变化并不重要。真正重要的是它揭示了一个结构性问题：

```text
AI Agent 越有用
  -> 它需要越多权限
  -> 它越像一个高价值攻击面
  -> 用户越不能把它当普通聊天软件部署
```

过去我们装一个笔记软件，最多担心同步服务泄露笔记。

以后我们装一个个人 Agent，它可能同时连着浏览器、终端、消息软件、邮箱、日历、文件系统和云服务。它不是一个应用，而是一组权限的集合。

这就是 OpenClaw 给我的最大提醒：AI Agent 的门槛不是“能不能跑起来”，而是“能不能在可控边界内跑起来”。

## OpenAI 招入创始人，是背书，也是张力

2026 年 2 月，Peter Steinberger 加入 OpenAI。TechCrunch 的报道里提到，OpenAI CEO Sam Altman 表示 Steinberger 将推动下一代个人 Agent，OpenClaw 则会继续作为开源项目存在，并由 OpenAI 支持。

这个安排很微妙。

从积极面看，它给 OpenClaw 带来了资源和背书。个人开源项目突然面对全球用户、安全事故、社区治理和企业需求，单靠创始人精力很难长期支撑。OpenAI 的支持至少说明：主流 AI 公司已经把“能做事的个人 Agent”当成重要方向，而不是边缘玩具。

但从另一面看，它也带来了张力。

OpenClaw 最打动人的地方，本来是本地优先、开源、可控、模型可替换。OpenAI 则是最典型的大模型中心化平台之一。当一个本地优先项目的创始人进入中心化 AI 巨头，社区自然会问：

```text
OpenClaw 会不会逐渐偏向 OpenAI 生态？
基金会治理是否足够独立？
开源项目的路线会不会被商业目标影响？
如果 OpenAI 自己推出类似 Agent 平台，OpenClaw 处在什么位置？
```

这些问题现在不一定有答案。

但它们很关键。因为 OpenClaw 不是普通工具，它承载的是一类用户对“个人 AI 控制权”的期待。如果这个期待被削弱，它最核心的叙事也会被削弱。

## 横向看，它不是 Manus，也不是 Claude Code

要理解 OpenClaw 的位置，需要把它和几个同类放在一起看。

| 工具 | 更像什么 | 主要优势 | 主要代价 |
|---|---|---|---|
| OpenClaw | 本地个人 Agent 基础设施 | 控制权强、可扩展、可自托管 | 配置复杂、安全责任落在用户身上 |
| Manus | 云端托管 Agent 产品 | 上手快、普通用户友好 | 黑盒、数据和权限交给平台 |
| Claude Code | 面向代码库的终端助手 | 编程工作流强、上下文理解好 | 主要场景是开发，不是全天候个人助理 |
| AutoGPT | 早期自主任务链实验 | 开创性强、概念影响大 | 可靠性和成本问题明显，很多体验停留在演示感 |

OpenClaw 和 Manus 的差别最能说明问题。

Manus 代表的是消费级产品路线：用户不想管部署、不想管配置、不想管安全策略，只想打开网页让 Agent 干活。它牺牲一部分控制权，换取更低的使用门槛。

OpenClaw 则更像技术用户路线：我愿意折腾安装、配置、沙箱、模型供应商、消息渠道和权限边界，因为我不想把整个工作流交给别人托管。

这两条路线并不是谁完全取代谁。它们更可能长期共存：

```text
普通用户
  -> 云端托管 Agent

开发者 / 自动化重度用户
  -> 本地或自托管 Agent

企业 / 合规场景
  -> 私有化、沙箱化、审计化 Agent
```

Claude Code 则是另一条线。它和 OpenClaw 都能在本地执行命令、读写文件、理解上下文，但 Claude Code 的中心是代码库，OpenClaw 的中心是个人助理。一个更像“程序员的协作同事”，一个更像“常驻的自动化管家”。

如果只看功能，它们有重叠；如果看使用场景，它们并不完全竞争。

## 我最后怎么理解 OpenClaw

看完 OpenClaw，我不觉得它只是一个“很火的开源项目”。

它更像一个信号：AI Agent 正在从演示阶段进入权限阶段。

演示阶段的问题是：

```text
它能不能理解任务？
它能不能规划步骤？
它能不能调用工具？
它能不能给我一个看起来不错的结果？
```

权限阶段的问题则完全不同：

```text
它能访问什么？
谁能给它发指令？
它的每一步有没有审计？
它出错时能不能回滚？
它被攻击时损失边界在哪里？
它依赖哪个模型、哪个平台、哪个社区？
```

OpenClaw 火，是因为它把“AI 能替我做事”这件事讲得很具体。

OpenClaw 危险，也是因为它真的开始替人做事。

所以我现在会这样看它：

> OpenClaw 的价值不只是一个产品，而是一个样本。它展示了个人 AI Agent 可能长什么样，也提前展示了这类系统必须面对的安全、治理和信任成本。

如果未来每个人都会有一个长期运行的 AI 助理，那么 OpenClaw 这类项目提出的问题会越来越普遍：

```text
我的 Agent 运行在哪里？
它听谁的话？
它能碰哪些东西？
它犯错时谁负责？
它背后的生态由谁控制？
```

这些问题，比“它用了哪个模型”更底层。
